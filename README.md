# Certificate Radar

Локальное веб-приложение для инвентаризации TLS-сертификатов: сроки действия, доверие, CN/SAN, слабая криптография, объяснимый риск, владельцы, уведомления и отчёты. Интерфейс и рекомендации — на русском языке.

## Быстрый запуск

Требуется Python 3.11+ с `venv`. Проверено на Windows с Python 3.13.7. Linux поддерживается кодом и `run.sh`; отдельный прогон на Linux в этой среде не выполнялся.

Windows (PowerShell):

```powershell
cd C:\PROJECTS\KGM
Copy-Item .env.example .env  # только при первоначальной настройке
.\run.bat
```

Linux:

```sh
cp .env.example .env  # только при первоначальной настройке
sh run.sh
```

Открыть **http://127.0.0.1:8000**. Проверка готовности: `GET /health` → `{"status":"ok"}`. Скрипт создаёт `.venv`, устанавливает зависимости, создаёт `data/radar.db` и запускает Uvicorn. При неизменных зависимостях повторный запуск не обращается к pip или интернету. Прерывание — Ctrl+C. Запускайте один экземпляр приложения, без нескольких Uvicorn workers.

Параметры адреса и порта задаются в `.env`: `HOST=127.0.0.1`, `PORT=8000`. Для показа с другого устройства: `HOST=0.0.0.0`, `PUBLIC_URL=http://<IP компьютера>:8000`. Для изолированных запусков доступны `DATA_DIR` и `LOG_DIR`; относительные пути считаются от корня проекта.

### Подготовка офлайн

Chart.js и его лицензия включены в `app/static/vendor/`, CDN и внешних шрифтов нет. Само сканирование и все отчёты работают без интернета; цели должны быть доступны в локальной сети. Внешние уведомления требуют связи с выбранным каналом.

Один раз на машине с интернетом подготовьте пакеты **для той же ОС, архитектуры и версии Python**, которые будут на стенде:

```powershell
python -m pip download -r requirements.txt -d wheelhouse
```

Перенесите проект вместе с `wheelhouse/` на стенд. `run.bat` / `run.sh` автоматически установит пакеты с `--no-index`. Каталог пакетов не хранится в Git. Без `wheelhouse` интернет нужен только для первичной установки или изменения зависимостей. В рабочей директории разработки подготовлен wheelhouse для Windows x64 / Python 3.13.

## Локальный TLS-стенд

После установки зависимостей:

```powershell
.venv\Scripts\python.exe -m lab.generate_certs
.venv\Scripts\python.exe -m lab.lab_server
```

На Linux используйте `.venv/bin/python`. При запрете на порт 443 стенд переключится на 8443; также можно явно передать `--port 8443`. В таком случае добавьте `:8443` к демо-целям. Установка системных сертификатов или прав администратора приложению не нужна.

Добавьте строки из `lab/hosts.txt` в `C:\Windows\System32\drivers\etc\hosts` или `/etc/hosts` с правами администратора. Это ручное действие: генератор и приложение системный файл не меняют. Сервер по умолчанию слушает **127.0.0.1**; `dead.lab.local` указывает на **127.0.0.2**, где сервер не запущен. Параметр `--bind` позволяет выбрать другой адрес. Bind на `0.0.0.0` сделает `127.0.0.2` доступным и изменит ожидаемый результат dead.

Генератор создаёт root, intermediate и rogue CA, а также PEM/fullchain/PFX для всех сервисов. Только лабораторный root копируется в `data/trusted_ca/`. Закрытые ключи остаются в игнорируемом `lab/certs/`; пароль демонстрационных PFX — `lab`. Weak содержит настоящую SHA-1 подпись и RSA 1024. Даты относительно момента генерации с запасом 12 часов, чтобы целое число дней сохранялось на протяжении демонстрации. После повторной генерации перезапустите стенд: работающий сервер держит старые сертификаты в памяти.

| Имя | Ожидаемый результат |
|---|---|
| valid / wildcard | OK, доверенная цепочка, совпадение имени |
| info / warn / soon | 45 / 25 / 10 дней, INFO / WARNING / CRITICAL |
| vpn | 5 дней, владелец и criticality=critical из CSV, риск **91 Critical** |
| expired | EXPIRED, истёк 5 дней назад |
| selfsigned | Самоподписанный сертификат |
| untrusted / nochain | Недоверенный CA / отсутствующий intermediate |
| mismatch | SAN другого имени |
| weak | RSA 1024 и SHA-1; системная проверка также может отклонить цепочку |
| dead | ERROR / недоступен |

Без изменения hosts доступна CLI-диагностика с явным IP подключения:

```powershell
.venv\Scripts\python.exe -m app.collectors.tls_collector soon.lab.local --connect-host 127.0.0.1
```

При обычном сканировании приложение использует настоящий DNS и не подменяет ответы. Тесты создают собственный стенд на свободном порту и изолированно подменяют разрешение лабораторных имён внутри процесса теста. `lab/targets_public.txt` содержит резервные публичные цели; их сканирование запускается только по явному выбору пользователя и требует интернета.

## Демо за 5–7 минут

1. Запустите приложение и стенд, настройте hosts.
2. На `/scan` нажмите **«Вставить демо-CSV с владельцами»**, затем **«Применить сведения из списка / файла»**. Это назначает VPN владельца и критичность, необходимые для примера 91/100.
3. Нажмите **«Вставить демо-список»**, проверьте 15 уникальных целей (13 имён + два IP из CIDR), затем **«Сканировать»**.
4. Dashboard: KPI, диаграммы, топ рисков, VPN = 91. Проверьте фильтры статуса, владельца и издателя, поиск по CN/SAN, сортировку всех колонок.
5. Откройте nochain, mismatch и weak: причины, рекомендации, атрибуты сертификата и история.
6. Назначьте владельца nochain — риск уменьшится на 10 без сканирования. Изменение критичности также пересчитывает риск сразу.
7. Если настроен канал, покажите полученную сводку. Повторный скан не дублирует отправку; **«Отправить уведомления»** игнорирует дедупликацию.
8. Скачайте Excel с тремя листами, откройте `/report`, нажмите **«Печать / PDF»**.
9. В настройках измените `info` с 60 на 40: info станет OK. Для перехода в WARNING задайте **одновременно info=60 и warning=50**. Комбинация info=40, warning=50 отклоняется согласно правилу `info > warning > critical`.
10. Покажите CA и журнал `/audit`. Верните исходные пороги 60/30/14 перед следующей демонстрацией.

## Уведомления

Реквизиты задаются только в `.env`, затем приложение перезапускается:

- Telegram: `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`. Бот должен иметь доступ к выбранному чату.
- Email: `SMTP_HOST`, `SMTP_PORT` (587), `SMTP_USER`, `SMTP_PASSWORD`, `SMTP_FROM`, `SMTP_TO`. Подключение требует STARTTLS с проверкой сертификата.
- Teams: `TEAMS_WEBHOOK_URL`, совместимый с Incoming Webhook / MessageCard. Доступность этого типа webhook зависит от конфигурации Microsoft 365; неподдерживаемый канал возвращает явную ошибку.

На `/settings` показаны состояние каналов и маскированные значения, есть кнопки «Тест» и отправки сводки. Если реквизитов нет — «не настроено». Неуспешная отправка видна в UI и журнале, скан сохраняется. Повторная попытка после ошибки разрешена.

После скана отправляется одна сводка на канал: наименьший достигнутый порог из 60/30/14/7/1, для истёкших — 0. Уникальный ключ: `(thumbprint_sha1, threshold_days, channel)`. Новый сертификат начинает новую историю. Большие списки сокращаются до размера одного сообщения со ссылкой на полный Dashboard. Кнопка принудительной отправки повторяет текущую сводку.

Транспорты проверены с подменёнными HTTP/SMTP; реальные реквизиты не предоставлялись, внешние сообщения во время разработки не отправлялись. Протоколы: [Telegram sendMessage](https://core.telegram.org/bots/api#sendmessage), [Teams Incoming Webhook](https://learn.microsoft.com/en-us/microsoftteams/platform/webhooks-and-connectors/how-to/add-incoming-webhook).

## Статусы, риск и доверие

Статус зависит только от срока: OK >60, INFO 31–60, WARNING 15–30, CRITICAL 0–14, EXPIRED <0; ERROR — сертификат не получен. Дни считаются с `floor` в UTC. Остальные проблемы отображаются отдельно в Issues и Risk.

Риск: срок даёт 0/15/35/55/70/80 баллов; самоподпись +20 или ошибка цепочки +25, несовпадение имени +25, слабая криптография +15 за всю группу, отсутствие владельца +10. Множители low/normal/high/critical: 0.85/1/1.15/1.3. Итог `min(100, round(sum × multiplier))`, ERROR → null. Из-за округления и ограничения 100 видимое снижение после назначения владельца может отличаться от 10×множитель. Все слагаемые объясняются в карточке сервиса.

Для получения сертификата используется разрешающий TLS-контекст; отдельное подключение проверяет доверие системным хранилищем и загруженными CA. Имя проверяется отдельно по SAN, с CN fallback при отсутствии SAN. Wildcard покрывает ровно один левый DNS-лейбл. AIA используется для подсказки, сертификаты из AIA не скачиваются. Ошибки OpenSSL 20/21 честно обозначаются «неполная цепочка или недоверенный CA»: только по этому коду точную причину различить нельзя. Проверки отзыва OCSP/CRL в MVP нет.

Публичные корневые CA загружаются через `/settings`: PEM/CRT/CER, DER конвертируется в PEM, leaf и private key отклоняются. Файлы сохраняются под отпечатком SHA-256. Изменение списка CA влияет на следующий скан, старые наблюдения сохраняются.

## Архитектура

```text
Текст / TXT / CSV / CIDR
          │ parser.py → Target
          ▼
BaseCollector → TLSCollector (socket + ssl, два TLS-handshake)
          │ RawObservation (DER, TLS, IP, trust)
          ▼
analysis: cert_parser → hostname → checks → status → risk
          │
          ▼
scanner → SQLAlchemy 2 → SQLite (data/radar.db)
          │
          ├── FastAPI JSON API → Jinja2 + vanilla JS + локальный Chart.js
          ├── exporters → CSV / XLSX / HTML для печати
          ├── BaseNotifier → Telegram / SMTP / Teams → дедупликация
          └── audit → SQLite + logs/audit.log; диагностика → logs/app.log
```

Реестр `app/analysis/checks.py`: новая проверка — функция `check(result, endpoint, settings) -> Issue | None` и регистрация в `CHECKS`. Новый тип сбора реализует `BaseCollector`, новый канал — `BaseNotifier`. Одновременно выполняется один скан с пулом до 32 TLS-задач по умолчанию. Запись в SQLite последовательная, WAL позволяет читать результаты во время сканирования. Dashboard показывает последний `scan_id` отдельно для каждого endpoint; непересканированные сервисы остаются видимыми. Прерванные перезапуском сканы помечаются failed.

API документирован локально на `/docs`; маршруты перечислены в `SPEC.md`, раздел 7. Дополнительно: `POST /api/endpoints/import` для сведений без скана, `GET /api/demo-targets?csv=true`, `GET /api/notifications` для состояния каналов. История доступна через `GET /api/endpoints/{id}`. CSV с непустыми полями обновляет сведения, пустые поля сохраняют прежние значения. Очистить владельца можно через PATCH/карточку.

## Безопасность и границы MVP

- К целям выполняются только TLS-рукопожатия, без HTTP-запросов, логинов, изменений и автоматического перевыпуска.
- По умолчанию слушается loopback. Авторизация пользователей не входит в MVP; доступ к интерфейсу даёт возможность сканировать заданные цели и менять настройки.
- Файл `.env`, БД, логи, сгенерированные ключи и сертификаты стенда исключены из Git. Секреты не записываются в БД и маскируются в диагностике/журнале.
- Ограничения: файл до 1 МБ, 2048 целей за скан, CIDR до 1024 адресов по умолчанию. Невалидный список нужно исправить перед запуском.
- Jinja autoescape и DOM `textContent` защищают отображение данных; текстовые ячейки CSV/XLSX не исполняются как формулы.
- Сбор информации по публичным или рабочим адресам начинается только после ввода целей и запуска сканирования пользователем.
- Автоскан, IIS setup, редактирование весов в UI, экспорт отфильтрованного набора и Prometheus `/metrics` — опциональные пункты ТЗ, в этот MVP не включены.

## Проверки

```powershell
.venv\Scripts\python.exe -m pytest -q
.venv\Scripts\python.exe -m pytest -m lab -q
.venv\Scripts\python.exe -m pytest tests/test_demo.py -q -s
```

Тесты автоматически поднимают локальный TLS-стенд, не требуют hosts, порта 443 или интернета. БД и логи тестов находятся в `.test-artifacts/`; база перед каждым API-тестом создаётся заново. Настройки внешней отправки принудительно отключены. `test_demo.py` дважды проходит сценарий с чистой базой и проверяет 50 целей за <15 секунд. Тесты покрывают парсер, SAN/CN, все сценарии TLS, статусы, каждый Issue, риск, API, владельцев, экспорт, CA, журнал и дедупликацию.

Проверка в Chrome: полный путь от пустой базы до скана, 15 строк, два графика, фильтры, сортировки, карточка/владелец, настройки/CA, аудит и печать PDF; ширина 1280 px. Созданный XLSX открыт установленным Excel в режиме только чтения. Детали выполнения шагов и проверки — в `PROGRESS.md`.

## Развитие

Infrastructure Risk Radar: Identity / DNS / Service / Patch / Backup Radar. Текущие интерфейсы отделяют наблюдения, проверки и выводы, поэтому новые коллекторы и проверки можно добавлять независимо от Dashboard и хранилища.
