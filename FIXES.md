## Приоритет 1 — ошибки анализа (влияют на результаты и демо)

### Fix 1. Проверка доверия: устаревший TLS и слабая криптография не должны давать ложную ошибку цепочки

**Файл:** `app/collectors/tls_collector.py`, метод `TLSCollector.verify`.

**Проблема A (TLS 1.0/1.1).** Подключение B использует `ssl.create_default_context()`, в котором минимальная версия — TLS 1.2. Для сервиса, поддерживающего только TLS 1.0/1.1, рукопожатие падает с `ssl.SSLError` (не `SSLCertVerificationError`), и результат получает `chain_status="error"` → ложный `CHAIN_UNTRUSTED` (+25 к риску).
Воспроизведение: `tls-v1-0.badssl.com:1010` → сейчас `chain=error`, issues `CHAIN_UNTRUSTED` + `OLD_TLS`.

**Проблема B (слабый ключ/подпись).** Для `weak.lab.local` OpenSSL на уровне безопасности по умолчанию отклоняет сертификат с `verify_code=66` («EE certificate key too weak»). Сейчас это классифицируется как `chain_status="error"` → `CHAIN_UNTRUSTED` с рекомендацией «установить промежуточные сертификаты», что неверно. По `SPEC.md` 9.1 для weak ожидаются только `WEAK_KEY` + `WEAK_SIGNATURE`. Слабая криптография уже отражается отдельными проверками — цепочка должна оцениваться только по доверию.

**Решение:**
1. Вынести построение проверочного контекста в функцию `verification_context(legacy: bool) -> ssl.SSLContext`:
   - общая часть: `ssl.create_default_context()`, `check_hostname=False`, `verify_mode=CERT_REQUIRED`, загрузка всех `*.pem|*.crt|*.cer` из `trust_dir`;
   - при `legacy=True` дополнительно (в `try`, как в `observation_context`): `minimum_version = TLSv1`, `set_ciphers("DEFAULT:@SECLEVEL=0")`.
2. Алгоритм `verify`:
   - Попытка 1 — строгий контекст (`legacy=False`). Успех → `valid`, как сейчас.
   - Повторить **один раз** с `legacy=True`, если попытка 1 завершилась:
     - `ssl.SSLCertVerificationError` с `verify_code` ∈ `{66, 67, 68}` (EE_KEY_TOO_SMALL, CA_KEY_TOO_SMALL, CA_MD_TOO_WEAK), или
     - `ssl.SSLError`, который **не** является `SSLCertVerificationError` (ошибка рукопожатия / версии протокола).
   - Не повторять при таймауте, отказе в соединении и прочих `OSError`, не являющихся `ssl.SSLError`.
   - Результат повторной попытки классифицировать по существующей таблице `CHAIN_CODES` (раздел 6.3 SPEC).
   - Если повторная попытка использовалась, к `chain_message` добавить пояснение: `«; проверено с пониженным уровнем безопасности OpenSSL (устаревший TLS или слабая криптография)»`. Для случая B дополнительно сохранить исходный текст OpenSSL (например, `«по умолчанию отклонено: EE certificate key too weak»`).
   - Порядок `except`: `SSLCertVerificationError` раньше `SSLError`, `SSLError` раньше `OSError`.
3. Сравнение DER между подключениями A и B (`«Сертификат изменился между двумя подключениями»`) сохранить.

**Ожидаемые результаты:**
| Цель | chain_status | Issues |
|---|---|---|
| `weak.lab.local` | `valid` | `WEAK_KEY`, `WEAK_SIGNATURE`, `NO_OWNER` (без `CHAIN_UNTRUSTED`), риск 25 Medium |
| сервер только TLS 1.0 с доверенным сертификатом | `valid` | `OLD_TLS` (без `CHAIN_UNTRUSTED`) |
| `nochain`, `untrusted`, `selfsigned`, `expired` | без изменений | без изменений |

**Тесты:**
- `tests/test_collector_lab.py`: для `weak` ожидать `valid`; проверить, что в `chain_message` есть «пониженным уровнем».
- Новый тест (`@pytest.mark.lab`): в тесте поднять TLS-сервер с сертификатом `valid` из `lab_material`, серверный контекст с `minimum_version = maximum_version = TLSv1` и `set_ciphers("DEFAULT:@SECLEVEL=0")`. Если OpenSSL не позволяет — `pytest.skip` с пояснением. Ожидать `tls_version == "TLSv1"`, `chain_status == "valid"`, и после `analyze` — `OLD_TLS` есть, `CHAIN_UNTRUSTED` нет.
- `tests/test_demo.py`: добавить проверку, что у `weak.lab.local` нет `CHAIN_UNTRUSTED`.

### Fix 2. Баннер «Последняя ошибка уведомлений» не должен висеть вечно

**Файлы:** `app/api/notifications.py`, `app/static/notifications.js`.

**Проблема:** `GET /api/notifications` возвращает последние 10 событий `notification_failed`, а JS показывает красный баннер, если список не пуст. Одна неудачная попытка (например, на репетиции) — и баннер висит на Dashboard и в Настройках навсегда, даже после успешных отправок.

**Решение:**
- В ответ `GET /api/notifications` добавить поле `last_error: str | null`: найти **самое последнее** событие аудита с `action ∈ {notification_sent, notification_failed}`; если это `notification_failed` — вернуть его `details.error`, иначе `null`. Поле `failures` оставить для совместимости.
- В `notifications.js` показывать баннер только при `data.last_error`.

**Тест:** ошибка отправки → `last_error` заполнен; затем успешная отправка (замоканный notifier) → `last_error is None`.

### Fix 3. Разные издатели на стенде (фильтр по Issuer должен быть полезным)

**Файл:** `lab/generate_certs.py`.

**Проблема:** у всех сертификатов стенда (включая CA) `O = "Certificate Radar Lab"`. В Dashboard колонка «Издатель» = `issuer_o or issuer_cn`, поэтому в фильтре «Издатель» одно значение. А фильтр по Issuer — часть сценария демо (SPEC 12, п. 5).

**Решение:** добавить в `make_certificate` параметр `organization: str`, задать:
| Сертификат | O |
|---|---|
| Lab Root CA, Lab Intermediate CA | `Lab Corporate PKI` |
| Rogue CA | `Rogue Issuer Ltd` |
| `selfsigned.lab.local` (сам себе издатель) | `Self-Signed Test` |
| остальные leaf | `Lab Services` |

Ожидаемо после скана демо-списка в фильтре «Издатель»: `Lab Corporate PKI`, `Rogue Issuer Ltd`, `Self-Signed Test`, `—` (недоступные).

**Тест:** сгенерировать стенд во временный каталог, разобрать `valid`, `untrusted`, `selfsigned` через `parse_certificate` → три разных `issuer_o` с указанными значениями.
